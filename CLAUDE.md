# CLAUDE.md

Encela: an npm package (`encela`) that gives Claude Code one MCP server and a plugin. The user writes one request; Claude (the orchestrator, in the user's own session) writes a blueprint, the user approves it, and Encela assembles the pieces it names. Encela never calls a model itself.

Successor of `oceanstarlight/ai-management-pg-fo-desktop` (the desktop app is frozen; its catalog and `packages/encela` hub code were carried over).

## Terms

- Piece (부품): one thing a build can use. Runs: `mcp`, `cli`, `library`. Documents: `skill`, `rule`, `instruction`, `subagent`. One shape for all (`src/piece.ts`).
- Level (수준): how big a request is, sized by Claude or named by the user. Simple: Encela stays out. Medium: the light path (`quick_build`: a small blueprint, the approval and the assembly in one call). Difficult: the full flow (the orchestrate skill).
- Blueprint (설계도): goal, requirements, pieces with roles, workers, steps, choices. Kept in the project as `.encela/blueprints/<id>.json`.
- Assemble (조립): start the blueprint's MCP pieces, write working copies of its documents to `.encela/build/<id>/`. Only copies are adapted; pieces never change.
- Worker (작업자): a Claude Code subagent that does some of the steps.
- Pipeline (파이프라인): a chain of steps in a blueprint that Encela runs itself, passing data from piece to piece: tool steps (a tool of an MCP piece), transform steps (jq), claude steps (handed to Claude, the run waits). A run (실행) keeps its state and outputs in `.encela/runs/<run>/`.
- Recipe (레시피): a blueprint that worked, kept by the user to start the next build of its kind from.
- Marked call: a pipeline tool call that may change things or may reach outside (its server doesn't say otherwise). The user is shown each with its arguments when approving.

## Layout

- `src/piece.ts` piece shape, checks, what the user is warned about. `registry.ts` catalog + the user's `~/.encela/pieces.json`. `search.ts` keyword search.
- `src/blueprint.ts` blueprint shape, checks, rendering, storage, what an approval records. `assemble.ts` working copies and worker briefs. `seal.ts` the key in the user's Encela folder that makes an approval or a run count.
- `src/pipeline.ts` pipeline shape, checks before a run, `{{ }}` references, marks and fingerprints. `engine.ts` runs (scheduling, each, retries, waiting claude steps, state on disk, reports). `jq.ts` the expression language (own jq subset, cases recorded from jq 1.7 in `test/fixtures/jq-cases.json` and `jq-review-cases.json`; `jq-review-cases.gen.mjs` records the latter again where jq 1.7 is installed). `sandbox.ts` evaluates expressions in a worker thread with a time limit. `schema.ts` a small JSON Schema check. `tools.ts` cache of each MCP piece's tool list.
- `src/server.ts` the MCP server (20 tools, the hub that starts MCP pieces on demand, the approval gate, the pipeline tools). `client.ts` MCP client for the pieces. `spawn.ts` how a program is started on Windows (found on PATH by Encela, a `.cmd` handed to cmd.exe as one escaped line).
- `src/finder.ts` the GitHub finder (`github_search`, `github_read`, and `piece_add` with `from`): searches, reads a repository at a commit, drafts a piece from its README's `mcpServers` example, its manifest or a document file, and checks the package a start command names against npm or PyPI. Tested against stand-ins in the test's own process (`test/finder.test.mjs`).
- `src/recipe.ts` recipes (`recipe_save`, `recipe_get`, `encela recipes`): a finished blueprint kept in the user's Encela folder (`<home>/recipes/<name>.json`) without what belonged to that one build, found again by `find_pieces` and the prompt hook, handed back as a draft to adapt.
- `src/hook.ts` UserPromptSubmit hook: one short note on each prompt (the three levels), plus pieces and recipes only where the match is strong. `setup.ts` writes and installs the plugin. `cli.ts` the command.
- `src/live.ts` what Encela is doing right now, kept as `.encela/live.json` for the view: written before each tool's answer, and a moment after anything changes in between. Nothing reads it back.
- `plugin/` the plugin's static files: `skills/orchestrate/SKILL.md` (the orchestrator's instructions), `agents/assembler.md`, `agents/pipeliner.md`.
- `plugin/hooks/view.tsx` the view (작업 화면): a hooks module Claude Code runs itself, a pane (`/encela-view`) and one line above the prompt. `hooks/model.ts` works out what to show from the state alone, and how each line looks at each tick (no drawing, tested by `test/view.test.mjs`). `hooks/motion.tsx` is a surface module: where the surface redraws a region by itself (terminal, desktop app) Claude Code runs it on its drawing thread, and it moves the lines (spinners, a pulse, a light along the bar, a flash on change); elsewhere `view.tsx` draws them as they stand. `hooks/canvas.ts` is the pane's second tab, the workflow canvas (워크플로우 캔버스): the orchestrator, the subagents and pipeline runs it started, and the pieces and tools they reach for, laid out in cells for the room there is, with packets running along a line while one calls the other (tested by `test/canvas.test.mjs`). The tab shown is kept in `motion.tsx` (a press changes it at once) and remembered for the session by `view.tsx`. `types/index.d.ts` the shapes the server and the view share, and what the view keeps in the session's state. `tests/view.test.tsx` runs inside Claude Code (`pnpm check:view`), and stays out of the package.
- `.github/workflows/ci.yml` lint, typecheck and tests on Linux and Windows. `npm.yml` publishes a version of `package.json` that is not on npm yet when it reaches main (npm Trusted Publishing, no token stored; `scripts/check-pack.mjs` makes sure the package holds the built files). Raise the version to release.
- `docs/pipeline-design.md` why pipelines work the way they do (the draft, the critique, the decisions).
- `catalog/` bundled pieces: `builtin/`, `external/<source>/` (with LICENSE), `modules.json` (MCP servers, CLIs, libraries: not bundled, only how to start or add them). `build.mjs` turns it into `dist/catalog.json`. `candidates/` is research output: what was checked at its source, the manifest of converted documents, and `check_docs.py`, which prints how each bundled document differs from its source.

## Commands

```bash
pnpm lint        # Biome; `pnpm format` to fix
pnpm typecheck
pnpm test        # builds, then node --test
pnpm check:view  # the view, checked by Claude Code itself (`claude plugin validate` and `plugin test`)
```

Run the first three before committing, and `pnpm check:view` after touching `plugin/hooks`, `plugin/types` or `src/live.ts` (CI can't: it needs the `claude` command). To try it in Claude Code: `node dist/cli.js setup` (or `--no-claude` and `claude --plugin-dir ~/.encela/claude-plugin/plugins/encela`).

## Rules

- Nothing is assembled or run before the user approves the blueprint. The light path (`quick_build`) is no way around this: it is the same blueprint, question and assembly behind one call, and takes no workers, pipelines or choices. A piece Claude found outside (`origin: external`) is untrusted until a blueprint with it is approved. Don't add paths around this. Trust belongs to a piece as it was accepted: kept again with another command, text, file beside it, guide, source or license (`Registry.add`), it is untrusted again, `blueprint_assemble` refuses a blueprint that holds such a piece and sends it back for approval, warnings are never taken off an unchanged piece by a later `piece_add`, and Claude's `piece_add` never replaces a piece the user added. An approval counts for the pieces as they were when the blueprint was last shown (`shownAs` in `server.ts`): a piece swapped between the showing and the answer leaves the blueprint a draft. What a piece is started with, sent, and handed from the user's environment is in what the user is shown (`cautions`).
- The project folder is not trusted: a repository can ship its own `.encela/`. An approval and a run count only with this computer's seal (`src/seal.ts`); a blueprint without one is a draft, a run folder without one is ignored. Build every path under `.encela` with `inEncela` (it refuses links), write a run's files with the engine's `put`, and never take a path from a file in the project.
- Pipelines: a marked call runs only if the user saw it, as it is, when approving, and only after a direct approval (the user answered Encela's own question). "As it is" includes where it is, its `when` and `retry`, and every step and input that feeds it (`stepPrint`, `feeds` in `pipeline.ts`): anything new that decides what a marked call does belongs in that print and in the approval text. A question the client closed unanswered (Claude Code does this without a terminal) is not an answer: the approval is then relayed through Claude and marked calls stay off. A call whose fate is unknown (timeout, lost connection) is never repeated automatically unless the tool is known to be read-only or idempotent. The server reads and writes only inside `.encela/`. Expressions never run in the server's own thread.
- The view only watches. Its hooks hand every call on unchanged and never fail one (what goes wrong while watching is swallowed), and a session that calls no Encela tool pays one check per call. `.encela/live.json` is a file in the project, so the view takes it only as a plain file where Encela keeps it, in the folder the session was in when it first called Encela, written since then and not dated ahead of now, and reads it field by field (`parse` in `model.ts`). A line handed to `motion.tsx` holds no key without a value (Claude Code refuses such props and the pane goes blank), a frame keeps to its rows with the step in progress in it, and a tool's answer never waits for the view's reading. Claude Code lets `$` go only to functions declared at the top of the module: keep it that way or `claude plugin validate` fails. The canvas draws only what the view saw pass (who called what, while the call was out) and what the server's file says; a line never draws over a node, and every line keeps to the columns there are. Motion says that something is going on: nothing moves once Claude's turn is over and no run or call is out, and the clock then asks for no redraw. Colours are the theme's keys, never raw ones, and a worker's colour is none of those that say how things stand.
- The finder only reads: GET requests to GitHub's API, its raw file host at a named commit, and the npm and PyPI registries; nothing is cloned, run or written. A redirect to another host is not followed, answers are bounded, and one read makes a bounded number of requests. The user's `GITHUB_TOKEN`/`GH_TOKEN` goes to `https://api.github.com` alone and is kept nowhere. What a repository says is a stranger's text: cleaned, cut to size and handed to Claude inside tags it can't close, never as instructions; a value from a README's `env` is kept only when plainly harmless, and names that make a program load code are dropped. With `from` (a full commit), the source, license, warnings, a document's text and the kind are the finder's own reading, not what Claude passed, and the start command Claude passes is checked, pinned and cleaned like a README's. A package that doesn't name the repository as its source is never guessed into an install or start command, and the registry is asked only about the package a command really fetches (`packageOf` gives up on any option or spec it doesn't know). Outside the data tags there is Encela's own text only: no file name, example name or argument from the repository. Each call has its own count of requests, redirects included, and a registry that can't be asked is said so, never read as "not published".
- Recipes are a starting point and nothing more: a blueprint made from one is a draft and is approved like any other, and a choice's last answer is shown as a default, never filled in. A recipe is made only from a blueprint this computer saw built to its end, exactly as it then stood (`sealBuild`/`building`/`builtHere` in `blueprint.ts`: the seal is set at assembly and follows each step, so a file edited to say assembled or done, steps a file already called done, or a done blueprint saved again with other text, is refused). It lives only in the user's Encela folder (never in a project), and holds no approval, no step status, no request text, no pipeline input default and no environment value set for one build (only `${NAME}` references); what it does keep as written (goal, steps, pipeline arguments, notes) is said in `recipe_save`'s answer. Claude saves one only after the user said yes.
- What only the user can do for a piece (sign in, make a key, keep a program open) is in its `prepare`, shown with the blueprint and again at assembly; a later `piece_add` never takes a line off. Encela does no browser sign-in and stores no key: a server that needs one is added to Claude Code by the user.
- Never read, copy or store Claude credentials. Run the user's own `claude` only.
- Windows matters: the plugin's MCP command goes through `cmd /c`, the hook command must not (see `setup.ts`). Every program Encela starts goes through `launch` in `spawn.ts`, never `shell: true`: a bare name is looked for on PATH only (Windows would look in the project folder first), and arguments reach a `.cmd` whole. CI runs the tests on Windows.
- Text Claude reads (tool results, the skill) is English; Claude shows it to the user in their language.
- Bundled catalog content: only MIT, Apache-2.0, BSD, ISC, Zlib, Unlicense, CC0, at a pinned commit, with `license`/`copyright`/`source_*` frontmatter, the LICENSE text in `catalog/external/<source>/`, and a row in `THIRD_PARTY_NOTICES.md`. No scripts, hooks, ads, telemetry. Pieces the user fetches at run time are not bundled and only get warnings.
- Do not use "Claude" or "Anthropic" in the product's name or branding.

## Subagents

- Ask the user before running a workflow or spawning subagents.
- Simple or repetitive work, verification and fact-checking: model `sonnet`. Web research: `sonnet` or `haiku`.
- Heavy reasoning (design critique, hard implementation): `opus` is fine.
